## 2. Summary

The plan covers every scope bullet and acceptance criterion of the ticket, each with a named file and a named test, and its four design decisions are each stated with the rejected alternative and the reason. Its feasibility claims hold up: the exported allowlist accessor exists, the test helpers it reuses exist with the signatures it assumes, the root-package embed has no import cycle, and all four of its redocly claims (a `default` response does not satisfy `operation-4xx-response`; `security: []` and a license `identifier` pass; a JSON-flow closing bracket at the key's own column is rejected as "deficient indentation") reproduce on 2.63.0. The key concern is sequencing: the plan anchors on BC-5 @75530c0 and states "No SPEC edit is needed", but BC-5 has since added a SPEC clarification commit (fd15b4a) that changes three §5.3 parsing rules the operation description must document.

## 3. Issues

**[MAJOR] "Contract" header / "Shared files and sequencing" — The anchor is stale: BC-5 gained a SPEC commit after 75530c0, and the plan does not merge it.**
`feat/BC-5-search-api` is now at 1871b01 and contains fd15b4a ("docs(spec): clarify search parsing edge cases from BC-5 review"). Go code is unchanged versus 75530c0 (verified: `git diff 75530c0..HEAD -- backend/internal/httpapi/` is empty), but §5.3 gained three rules the search operation description is required to carry, and the plan was written from the worktree's older SPEC: (a) more than 10000 `&`-separated parameters is also `malformed_query`, and then nothing else is validated; (b) `city`/`keyword` lengths count Unicode code points (which is what OAS `maxLength` means, so the param descriptions can say so); (c) for a repeated scalar an empty first value is absent (`minPrice=&minPrice=5` is absent, not 5). The plan's description text currently says only "a repeated scalar uses its first value". fd15b4a also adds HTML comment markers above the §5.4 and §5.5 JSON blocks; `specExample` still works because it cuts on the next ```` ```json ```` fence after the heading, so test 4 is unaffected. Prompt note 1 already makes the merge binding ("If BC-5 gains commits, `git merge feat/BC-5-search-api`"), but the plan omits the step, so an implementer following the plan as written ships a description that contradicts the SPEC it will be reviewed against after the master merge.
**Recommendation:** Add as step 0 of implementation: `git merge feat/BC-5-search-api` (never rebase), then write the operation description from the merged §5.3. Fold the three clarifications into the outline: the 10000-parameter rule under `malformed_query`, "counted in Unicode code points" on `city` and `keyword`, and "an empty first value is absent" in the repeated-parameter sentence. Change "No SPEC edit is needed" to "No SPEC edit by BC-6; BC-5's fd15b4a is merged in".

**[MINOR] Decision 2 / "YAML footguns" — Two constructs the document will certainly use are missing from the reader's accept list.**
(1) The plan's own param descriptions say "absent: no filter", and the reader (correctly, like real YAML) rejects plain scalars containing `: `. Any description containing `: ` or ` #` must be double-quoted or a `|` block, and the footguns list does not say so. (2) The plan quotes response codes (`"200":`), so the reader must accept double-quoted mapping *keys*, but the accept list only mentions quoted *values*. An implementer who writes the reader from the list as given will fail on the first response block.
**Recommendation:** Add to Decision 2's accept list: double-quoted keys. Add to the footguns list: descriptions containing `: ` or ` #` go in double quotes or a literal block. Add to test 6's accept case a quoted key and a quoted value containing `: `.

**[MINOR] Tests, item 6 — The literal-block accept case should look like the real operation description.**
The search operation description is multi-paragraph, so the document will contain `|` blocks with blank lines inside them, followed by a sibling key at a shallower indent. Blank-line handling inside literal blocks (content, not terminator) and the `|-` chomp are the two places hand-rolled readers most often go wrong, and a one-line accept case will not catch them.
**Recommendation:** Make the accept case's literal block multi-paragraph (one blank line inside), with both `|` and `|-` present, each followed by a sibling key, and assert the exact decoded string.

**[MINOR] Decision 2 — The subset constraint lives only in test code.**
A future editor who adds a `>` folded scalar, an anchor, or an inline comment to `openapi.yaml` will see `TestOpenAPIParsesAsYAML` fail with a reader error and no pointer to the rule. The trade-off is acknowledged in the plan, but the cost to the next editor is avoidable.
**Recommendation:** A 4–5 line header comment at the top of `openapi.yaml` naming the subset (block YAML plus JSON flow; no anchors, tags, folded scalars, inline comments, or tabs) and pointing at `yamlsubset_test.go`. Reader errors should carry the line number and the violated rule. Full-line `#` comments are in the accept list, so the header is parseable.

**[MINOR] Validation step 6 — The lint expectation is pinned to a version the command does not pin.**
The "0 errors, 3 `operation-4xx-response` warnings" expectation was probed against 2.63.0 (the version in the local npx cache; I reproduced the result there). The validation command runs `@redocly/cli@latest`, which may resolve to a newer release with a changed recommended ruleset by the time validation runs.
**Recommendation:** Either run `@redocly/cli@2.63.0` or keep `@latest` (prompt note 5) and record the resolved version in the comment and validation attachment, so the result is reproducible and a ruleset drift is distinguishable from a document regression.

**[MINOR] Decision 4 / Risks — The `Proprietary` license entry is an invented claim to silence a warning.**
Verified on 2.63.0: with no `info.license` the recommended ruleset emits one `info-license` **warning**, not an error, so the ticket's "no errors" acceptance holds either way. The plan already surfaces this to the human as non-blocking, which is the right classification.
**Recommendation:** Default to omitting the license and accepting 4 justified warnings (the repo has no LICENSE file, and an SPDX `LicenseRef-Proprietary` is a legal assertion the author is not placed to make for interview code). Keep the human question as written; proceed under the omission default rather than blocking on it.

## 4. Positive Observations

- **Every claim is checkable, and the ones I checked hold.** `httpapi.SearchQueryParams()` is exported and returns a clone of the §5.3-ordered array; `serve`, `newTestRouter`, `newSearchRouter`, `assertRequestID`, `specExample`, `testOrigin` and `testNow` exist in `httpapi_test` with the shapes the tests assume; `newSearchRouter` wires Pinger, Searcher and Cities to the seeded store, so test 2's "every documented path answers with a documented status" is feasible for all four paths; BC-13's `.air.toml` really does watch `yaml` with `root = "."`; the `fallbacks` wrapper will give the new route the `GET, HEAD` Allow header the new `TestErrorEnvelopes` row expects.
- **The embed decision is correct and minimal.** `go:embed` cannot reach a parent directory; a root package `brillio/backend` that imports only `embed` keeps `openapi.yaml` where SPEC §3 puts it, avoids a SPEC edit, and cannot create an import cycle. The revive requirements (package comment, doc comments on `FS` and `OpenAPIPath`) are called out ahead of the lint run.
- **The stdlib-only tension is handled honestly.** The plan does not pretend a hand-rolled reader is a YAML parser; it states exactly what "parses as YAML" means (strict subset accepts, content checks against two independent sources, one real-parser run), names the fallback (a JSON-syntax document) and the size threshold that triggers it, and routes the dependency question to the human as non-blocking rather than quietly adding `go.yaml.in/yaml/v3` against SPEC §2 and the delegator brief's "hard limits" line.
- **Tests are mapped, not listed.** Each test cites the acceptance bullet or §8 case it discharges; the sync test is set-equality in both directions with a failure message that names what is missing on each side; test 1's byte-equality against `../../openapi.yaml` proves the embed serves the repo file rather than a stale copy; test 5 hard-codes the ten §5.5 codes including `malformed_query`, which run-state decision 03:00Z specifically requires BC-6 to carry.
- **Lint posture was probed, not assumed.** The reasoning for accepting three `operation-4xx-response` warnings (a `default` response does not satisfy the rule; documenting 405 under `get` would be untrue; a config file would be an orphan since the validator is not in `make check`) is sound and reproduces.
- **Validation is concrete and self-cleaning:** the run-state port, a byte-diff of the served body against the file, the 405 probe, and an `lsof` check after kill.
- **Sequencing respects the gate.** Review waits for BC-5 to land, the merge direction is stated (master into branch, never rebase), the only possible overlap (one router line) is identified, and `.lattice/` stays uncommitted.
