## 3. Issues

**[MAJOR] D2 / Risks item 3 — ListedDate wire-format decision needs a durable downstream handoff**
D2 correctly identifies that `time.Time` marshals as RFC 3339 and rejects `"2026-08-29"` on decode, and
resolves it by keeping `Listing` as the in-memory model with DTOs at the boundaries. That is the right call
under the ticket's "no logic" rule and §4's declared Go type (BC-5 needs its own item struct for `rank` and
`relevance` anyway; BC-4's seed needs per-field errors). But the blast radius is real: BC-3's ticket defines
`Scored{Listing; Relevance{...}}`, which embeds `Listing`, so the path of least resistance for BC-5 is to embed
`Scored` in its response item and ship `"listedDate":"2026-08-29T00:00:00Z"`. BC-5's acceptance test (a
`DisallowUnknownFields` round-trip) checks the key set, not the date format, so it would not catch this, and
the frontend date formatter (BC-8) expects `YYYY-MM-DD`. The JSON tags on `Listing` (required by the ticket and
by `TestListingJSONKeys`) make the struct look wire-ready, which sharpens the trap. The plan's mitigation is a
doc comment plus "the delegator forwards a one-line note to BC-4 and BC-5" with no stated channel; BC-3/4/5
delegators read `lattice show`, SPEC, context.md and run-state cold, none of which currently carry this.
**Recommendation:** Keep the design. Add a concrete step to "Shared files and downstream", executed when the
task reaches `review` (the moment the types freeze): `lattice comment` on BC-3, BC-4 and BC-5 saying
"`domain.Listing.ListedDate` is `time.Time`; the JSON tags name the wire keys only. Never `json.Marshal` /
`Unmarshal` `Listing` or `Scored` directly; parse and format with `domain.DateLayout` in your own record/DTO
structs." Mail the Orchestrator so the run-state shared-files row for `internal/domain` carries the same line.
Make the `ListedDate` doc comment prescriptive ("do not encode this struct to the wire; see `DateLayout`"), not
just a description of the tension.

**[MINOR] Tests table — httptest mode is unstated, and two rows need opposite modes**
"External package `httpapi_test`, run through `NewRouter` with `httptest`" is ambiguous between
`httptest.NewRecorder` and `httptest.NewServer`. Verified on go1.27.1: with a recorder, `HEAD /healthz` records
the body `{"status":"ok"}` (the recorder does not strip HEAD bodies; only the real server does), so the
`TestHealthz` row "HEAD 200 with empty body" fails under a recorder unless the handler special-cases HEAD,
which the plan does not ask for. Conversely, with `NewServer` and a default `http.Client`, `GET /x/../nope`
follows the 307 to `/nope` and lands on the 404 envelope, so the `TestErrorEnvelopes` 307 row fails under a
real server unless `CheckRedirect` stops it.
**Recommendation:** State the mode: `httptest.NewRecorder` throughout (simplest for the `request_id` and
`remote_addr` log assertions too). Change the HEAD row to assert status 200, Content-Type and X-Request-ID only,
and note that body suppression for HEAD is net/http's job (confirmed: the real server returns an empty body
with no handler changes). The 307 row is correct as written under a recorder (verified: status 307,
`Location: /nope`, pattern `""`).

**[MINOR] D7 — /healthz 503 branch overlaps BC-4's card**
The ticket defers the DB ping to BC-4 ("leave a `Pinger` interface in Deps that may be nil"); the plan
implements the 503 branch and the failing-Pinger test now. That is a reasonable, testable expansion and it
lets BC-4 ship a one-line change, but BC-4's card item 4 instructs BC-4 to add exactly this branch and test.
Without a note BC-4 will either duplicate the test or spend time discovering it is already done.
**Recommendation:** Keep D7. In the `lattice comment` to BC-4 recommended above, state that the 503 branch and
the failing-Pinger httpapi test already exist and that BC-4 only sets `Pinger: st` in `run()` (and may extend
the test with the real store).

**[MINOR] D1 — Startup validation broader than the ticket**
The ticket names LOG_LEVEL and SHUTDOWN_TIMEOUT as the startup errors. D1 also fails startup on PORT outside
1..65535 and on any CORS_ORIGINS entry that is not a bare `http(s)://host[:port]` (trailing slash, path, `*`,
zero entries). The reasoning is sound (a trailing slash would silently never match a browser's `Origin`; §5.6
has no wildcard) and a refused start is the better failure. The cost is a new rule that BC-13's compose file
and BC-15's README need to know about.
**Recommendation:** Keep it. Add one sentence to the `config` package doc comment listing the validation
rules so BC-13 and BC-15 can quote them, and mention the rule in the handoff to the Orchestrator. No SPEC edit
is needed; §11 is silent on validation.

## 4. Positive Observations

- Every ticket bullet, acceptance criterion and §8 httpapi/lint case maps to a named decision and a named
  test row. The acceptance-to-test table makes the code reviewer's and the Result Validator's jobs mechanical.
- The two non-obvious bets were probed on the host and the probes reproduce. `ServeMux.Handler` on go1.27.1:
  `POST /healthz` → pattern `""`, 405, `Allow: GET, HEAD`; `GET /nope` → `""`, 404; `GET /a/../nope` → `""`,
  307 to `/nope`; `HEAD /healthz` → `GET /healthz`; `OPTIONS /healthz` → `""`, 405 (so the "non-preflight
  OPTIONS gives 405" row holds). The planned `.golangci.yml` passes `config verify`, accepts the explicit
  `enable` list on top of `default: standard`, and revive's defaults flag package comments, exported-identifier
  docs and unused parameters exactly as D9 predicts.
- D4's middleware ordering is argued from consequences (request ID on every response including preflights and
  500s; the log line sees the recovered 500; CORS answers before routing), not asserted.
- D5 lists the rejected alternatives with the concrete failure of each (a catch-all swallows 405; twin
  patterns re-implement `Allow`; a writer rewrite cannot tell the mux's 404 from a handler's). This is the
  section a later agent would otherwise re-derive.
- Downstream seams are deliberate: `NewRouter` as the only registration site, handlers as methods on an
  unexported `api` with `writeError` taking `[]FieldError`, a linear `run()` so BC-4/BC-5/BC-6 insert
  contiguous blocks, no ticket numbers in shipped code, and the frozen-types rule tied to the `review`
  transition.
- D10's `dev-api` reasoning (build, then run from the repo root so §11's relative defaults resolve to `data/`)
  anticipates a BC-4-era breakage instead of fixing it later, and still honors the ticket's `go run ./cmd/api`
  acceptance in the validation script.
- The validation script is a single Bash call with port hygiene (`lsof` before and after), uses the built
  binary for the SIGTERM check because `go run` does not forward signals, and includes the config-error exit
  path, which is the one acceptance-adjacent behavior the unit tests cannot cover.
- Risks name their own detection (`TestErrorEnvelopes` catches `httpmuxgo121`; `core.excludesFile=/dev/null`
  catches the host ignore gap), and the `.gitignore` additions close both BC-1 review nits as the card asked.
