### 3. Issues

**[MINOR] Pager — CSS `.button` — Text-button tracking and hover color diverge from the demo**
The plan gives text buttons `letter-spacing: var(--tracking-button)` (+0.02em) and a hover that both underlines and switches to `oxblood-deep`, citing §3.2/§3.3 and §2.1. The reference implementation says otherwise: in `docs/branding-demo.html` only the primary `.btn` carries `letter-spacing: .02em`; `.link` (every text button, including the pager's) has none, and `.link:hover` only underlines with no color change. BRANDING §5.8 agrees: the Primary row lists +0.02em, the Text button row lists only "underline on hover with 3px offset". BRANDING's header names the demo as "the reference implementation of every token", so the plainer reading wins. The plan already flags this as a cross-ticket risk for BC-14 to reconcile, but neither BC-9 nor BC-10 has committed or drafted any component CSS yet (verified), so the cheap moment to align is now, not at BC-14.
**Recommendation:** Drop `letter-spacing` from `.button` (global.css already sets `letter-spacing: inherit` on buttons, so it inherits 0 from `.pager`) and make `.button:hover:not(:disabled, [aria-current='page'])` underline-only, matching `.link`. Then post a one-line `lattice comment` on BC-9 and BC-10 (or via the orchestrator) stating the text-button recipe BC-11 encodes: 13/1, 500, oxblood, no tracking, hover = underline 3px offset, focus-visible = 2px oxblood outline offset 3px, disabled = ink-3. If the planner prefers to keep oxblood-deep on hover, that is a design call for `lattice needs-human`, not a per-ticket choice.

**[MINOR] LoadingLine — resting track — Deliberate deviation from the ticket's literal wording needs a board-visible record**
The ticket says "2px track in line color under the filter bar; … Inactive renders the empty track so layout never shifts." The plan renders the inactive track transparent (2px box kept, no color) and puts `background: var(--line)` on `.active` only. The reasoning is sound and matches the demo (the app frame shows only the FilterBar's 1px hairline at rest; `.bar` appears only in the Loading panel), and L2/L3 preserve the layout-stability requirement. But the choice is recorded only in the plan's Risks list, and test L3 pins it (`.active` carries the `line` background), so anyone reading the ticket and the tests cold sees a contradiction.
**Recommendation:** Keep the transparent resting track. At implementation, record it as `lattice comment BC-11 "LoadingLine resting track is transparent (2px box kept); line color only while active, per demo. One-line flip if the owner wants a visible grey track."` and repeat it in the completion comment so BC-12 (which places the line under the FilterBar hairline) and BC-14 see it without reading the plan. Put the same sentence as a comment above `.track` in the CSS.

**[MINOR] StatusLine tests — S10 — `validationErrorBody` is the HTTP envelope, not a `ValidationError`**
The plan says S10 builds its error "from `validationErrorBody` shape: `{ kind: 'validation', … }`". The fixture is `ErrorBody` (`{ error: { code, message, fields? } }`) with `fields` optional; `ValidationError` requires `fields: FieldError[]`. The only converter in `src/api/errors.ts` is `parseErrorResponse(res: Response)`, which needs a `Response`, so an implementer reading the plan cold may go hunting or reach for `jsonResponse(...)` unnecessarily.
**Recommendation:** State the mapping in the plan: `const invalid: ValidationError = { kind: 'validation', message: validationErrorBody.error.message, fields: validationErrorBody.error.fields ?? [] }` (type-only import of `ValidationError` from `src/api/types`). Same for S11's `{ kind: 'network', message: 'Request failed.' }`.

**[MINOR] LoadingLine tests — L3–L5 — Source-text assertions are the right call under jsdom, but say what they do and do not prove**
Reading the stylesheet and asserting on its text is the pragmatic route (jsdom evaluates no media queries, Vitest returns CSS-module proxies, `?raw` is intercepted). The plan already keeps the regexes whitespace-tolerant for prettier. Two small hardenings keep these from becoming silent no-ops or false alarms.
**Recommendation:** (a) Assert `css.length > 0` once before the regex checks so a path mistake fails as "file empty" rather than "regex did not match". (b) Anchor the reduced-motion assertion to the `.segment` rule inside the `@media` block (e.g. match `@media \(prefers-reduced-motion: reduce\)\s*\{[^}]*\.segment\s*\{[^}]*width:\s*100%[^}]*animation:\s*none` with `[\s\S]` where needed) so a stray `animation: none` elsewhere cannot satisfy L4. (c) Note in the test file that these cases verify the shipped source, and that the visual behavior is proven by BC-12's browser validation.
